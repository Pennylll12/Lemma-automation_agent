# 意圖識別、自動填表與成交日規劃

適用版本：2026-11-03；Google模式。模型及本地識別均不會建立預約或改動日曆，測試入口不發WhatsApp。

## 工作台操作

1. 保持現有`.env`的Google／DeepSeek憑證、`CALENDAR_MODE=google`、`LIVE_SEND_ENABLED=false`。
2. 更新後重啟API及Worker，強制重新整理工作台。
3. 直接輸入客人訊息，點「發送測試訊息」，Worker會自動識別、查日曆或追問。完成識別後表單會回填，無需逐欄輸入。
4. 想先檢查，可展開「Google 日曆查詢條件」，點「識別並填入條件」。此按鈕只識別、不查日曆、不建立任務；發送後Worker會重新識別及查最新日曆。
5. 「只查日曆候選時段」在自動模式且有訊息時，也會先識別。資料不足便不查日曆。
6. 手動修改任一查詢欄位，會自動勾選「人工覆寫」。此時以表單為準，不再從文字改寫條件；取消勾選便恢復自動識別。
7. 新一輪測試預設不沿用上次客人資料。要模擬同一客人追問，取消「新一輪測試，不沿用上次客人資料」，並保持同一測試聯絡人。只沿用24小時內上一筆資料，不跨聯絡人、不從AI舊回覆提取日期。

## 分流

| 情境 | 行為 |
|---|---|
| 已有領匙日期、時間 | 最少預留一小時；指定「同日」只查當日，沒有空位不自動改查其他日 |
| 只有領匙日期 | 追問領匙時間，不假設上午或下午 |
| 指定驗樓日期／週末 | 只查該日／週末；未知面積先按3小時，不能據面積自訂需時對照 |
| 只有成交日期 | 估算領匙窗口，先查驗樓空位，再倒推領匙方案 |
| 下午／晚場 | 依偏好篩選；明確晚場才包括平日18:00 |
| 改期、取消 | 回覆交人工核對，不改動原預約 |
| 其他問題 | 回覆交同事跟進，不查日曆 |
| 日期矛盾、不明確、多個替代日期 | 追問；不把模型猜測當作查詢條件 |

## 日期、時間與模型邊界

啟用DeepSeek時請設定`AI_PROVIDER=deepseek`及既有`DEEPSEEK_API_KEY`。DeepSeek提取意圖及逐字原文片段，後端驗證片段確實在訊息內，再換算日期。模型不生成空位或領匙承諾；模型失敗或無key時用本地規則識別，並在內部標示來源。

支援明確年月日、香港日/月寫法（`5/11`為11月5日）、今天／明天／後日、星期幾／下星期幾、週末、本月／下個月指定日。按訊息接收當日的香港日期換算。未寫年份先用接收當年並顯示；若已過期會追問，不自動跳下一年。裸寫`11點`無上午／下午會追問，`11:00`按24小時格式。暫不保證理解所有口語、英文日期、農曆、多段日期範圍及複雜更正；請檢查表單並用人工覆寫。

前端識別預覽可能與稍後Worker識別有差異；實際任務保存`understanding`（意圖、來源片段、注意事項）、`resolved_schedule`及日曆快照，便於核對。原始`schedule`只保存人工傳入值，保持事件去重判斷不變。

## 成交日規劃

已按擁有者確認：**星期一至六為工作天，排除香港公眾假期**。配置為：

```dotenv
CALENDAR_BUSINESS_WEEK=mon_sat
```

預設亦為mon_sat。可選mon_fri只供業務規則日後明確修改。假期日期來自[政府1823官方資料](https://www.1823.gov.hk/en/hong-kong-public-holidays-ical)，已附2025–2027日期快照，超出涵蓋年份拒絕自動推算，需更新`backend/hk_holidays.json`。

目前採**成交翌日起算第一個工作天**作估算口徑，並在回覆顯示。這個起算方式未經律師樓或管理處確認，不應當成法律或合約截止日。最快第二個工作天領律師信，再兩個工作天作最早領匙估算；第10工作天作建議窗口邊界。仍須確認實際領信、致電日期、管理處可約日及辦公時間。

先查估算領匙窗口起的日曆忙碌，再產生最多兩個「驗樓候選＋建議向管理處查詢的領匙日期」方案。下午場可倒推最遲一小時前完成領匙，但不代表管理處該時間有開門。09:00驗樓不假設08:00可以領匙，會找前一個可領匙工作天；星期日驗樓亦建議提前領匙。所有領匙日期避開星期日及公眾假期、不超出估算窗口。若找不到方案或窗口已過，追問／交人工。

例如11月5日（2026年星期四）成交：11月7日為最快領信估算，11月10日為最早領匙估算。只有Google真實回傳當日無衝突且符合其他規則，才可以建議11月10日12:30驗樓、向管理處查詢最遲11:30完成領匙的安排。這些是待確認方案，沒有保留時段。

飯點、交通及驗樓師容量仍按Google指南處理，未知時全部候選須人工核實。Google Form登記查詢仍未接入，不會宣稱已核對登記或付款。

## 測試樣本

先以不同「新一輪測試」分別測試；以下日期為2026年例子，實測需保持日期未過。

| 客人訊息 | 期望 |
|---|---|
| 我11月5日上午11點攞鎖匙，想同日驗樓 | 自動填11/5、11:00、查1天；09:00不可推薦 |
| 我11月5日下午3點領匙，想同日驗樓 | 15:45不可推薦；沒有合適場次就說沒有，不默默換日 |
| 我11月5日成交，應該幾時攞鎖匙同驗樓？ | 自動成交日規劃，查估算可領匙後的真實驗樓空位，倒推方案 |
| 想約週末下午驗樓 | 只查週末下午，不能推平日或上午 |
| 我11月8日上午11點領匙，想同日驗樓 | 星期日領匙先確認，不能直接承諾 |
| 我11月5日攞鎖匙，想同日驗樓 | 追問幾點；同客人再答「上午11點」可補齊（需取消新一輪測試） |
| 想約11月5日星期六驗樓 | 日期與星期矛盾，追問 |
| 想取消之前個預約 | 交人工，不能聲稱已取消 |

## API

新增`POST /api/intent/interpret`，Admin Bearer，body為`message`、`contact_id`及可選`reset_context`。回傳意圖、欄位、可執行`schedule`或追問，不查Google、不發送、不建立任務。

Google模式下`/api/test/messages`或normalized webhook沒有`schedule`時，Worker會自動識別。提供`schedule`視為人工明確覆寫。可傳`reset_context:true`開始新情境；預設false供真實同客人對話。相同事件ID更改reset_context也會拒絕。

`AvailabilityRequest`新增`plan_from_completion`、`weekend_only`；`preference`新增`evening`。原手動Calendar API保留相容行為：要由成交日規劃需顯式`plan_from_completion:true`，自動識別成交意圖會代填。
